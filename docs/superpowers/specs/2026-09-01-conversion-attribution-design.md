# Huitaipcb Conversion Attribution Design

**Date:** 2026-09-01

**Status:** Design approved in chat; awaiting written-spec review

**Scope:** Local code, tests, documentation, and a prepared Supabase migration only

**Out of scope:** Production migration, GA4 Admin changes, deployment, commit, push, live test inquiries

## 1. Objective

Build one auditable conversion chain in which one successfully saved website inquiry has:

- one database `inquiries` row;
- one stable inquiry ID used only inside Huitai systems;
- one application idempotency key that prevents duplicate insertion on retry;
- one non-PII analytics event ID stored beside the inquiry;
- at most one server-confirmed GA4 `generate_lead` attempt;
- explicit file, administrator-email, customer-email, and analytics statuses;
- sanitized acquisition fields that can be reconciled with SEO, AEO, and GEO traffic.

The business definition of a lead is: **the API has successfully inserted or recovered an existing idempotent inquiry row**. File, email, or analytics failures must not erase that lead, but those failures must be visible and must not be represented as fully successful side effects.

## 2. Confirmed Starting State

- The browser currently emits three synonymous success events after a 2xx response: `contact_form_submit`, `rfq_submit_success`, and `generate_lead`.
- GA4 misses real browser-side success events; a genuine inquiry on 2026-08-31 was saved and emailed but had no GA4 success event.
- GA4 Enhanced Measurement emits automatic `form_start`, while the form also emits a manual generic `form_start`.
- The API inserts an inquiry before validating every file.
- Storage and `inquiry_files` errors can be ignored while the API continues.
- Resend returns `{ data, error }`; the current route relies mainly on exceptions.
- The database does not store idempotency, attribution, email-delivery, file-processing, or analytics-delivery fields.
- There is no unit-test runner or Supabase migrations directory in the repository.
- `src/lib/email/resend.ts` contains pre-existing user brand-copy changes from `Huitai Electronics` to `Huitai PCB`. They must be preserved.

## 3. Selected Architecture

Use an inline, server-confirmed state chain inside the inquiry API. The API remains the orchestration boundary, but validation, attribution sanitation, email delivery, analytics delivery, and status mapping are extracted into focused modules with dependency injection for tests.

The selected approach intentionally does not add a queue, cron job, or background worker. Failed side effects are recorded for later review; automatic background retries are deferred because the project currently has no durable job infrastructure.

## 4. Canonical Event Model

### 4.1 Primary business conversion

`generate_lead` is the only canonical form-success event.

- It is sent by the server only after the inquiry row exists.
- The browser does not emit it.
- The server attempts it at most once during the original successful request.
- An idempotent duplicate request returns the existing inquiry and does not resend an event already marked `sent` or currently `pending`.
- Analytics failure changes `analytics_status` but does not change the saved inquiry or the API's business-success result.

### 4.2 Diagnostic and micro events

- Stop emitting `contact_form_submit` and `rfq_submit_success` as synonymous client success events.
- Keep `quote_click`, `whatsapp_click`, and `email_click` as ordinary interaction events.
- Keep `quote_cta_click` as a submit-attempt diagnostic event.
- Remove the manual generic `form_start` and retain `rfq_form_start` as the reliable business-funnel start.
- Remove the custom `contact_page_view`; use GA4's normal `page_view` filtered by `/contact` and `/de/contact`. This prevents language-path omissions.
- Retain `rfq_file_upload` as a file-selection event, clearly documented as a selection batch rather than proof of server upload.

GA4 Admin must later be changed manually so only `generate_lead` represents a primary website lead. Code must not claim that this Admin change has happened.

## 5. Correlation and Privacy

### 5.1 Identifiers

- `inquiry.id`: internal business identifier; never sent to GA4.
- `idempotency_key`: UUID generated once per unsent form journey, persisted in `sessionStorage`, and reused across network retries or same-tab reloads; stored in the database; never registered as a GA dimension. It is cleared and rotated only after the browser receives a saved-inquiry response.
- `analytics_event_id`: independent random UUID generated by the server, stored with the inquiry, and sent to GA4 as `event_id`.
- The application, rather than GA4, enforces at-most-once delivery by checking persisted analytics status. The design does not assume GA4 automatically deduplicates arbitrary events by `event_id`.

### 5.2 Prohibited analytics data

Never send the following to GA4:

- name;
- email;
- telephone number;
- company contact details;
- message or technical brief;
- full file names;
- inquiry ID;
- raw query strings that might contain PII.

### 5.3 Acquisition sanitation

The client may provide only:

- `page_path` and `landing_page`: pathname only, beginning with `/`, without query or hash;
- `referrer`: origin plus pathname only, without query, hash, credentials, or fragment;
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`: allowlisted values with whitespace normalization and strict length caps;
- `ga_client_id`, `ga_session_id`: validated pseudonymous GA identifiers.

Unknown form fields and arbitrary URL query parameters are discarded. Missing GA identifiers do not block the inquiry. For Measurement Protocol counting without a browser client ID, the server uses the independent analytics event UUID as a pseudonymous fallback client identifier; such a lead is expected to remain unattributed rather than being assigned a fabricated channel.

Add correlation fields:

- `idempotency_key uuid`
- `analytics_event_id uuid`
- a unique partial index on non-null `idempotency_key`
- a unique partial index on non-null `analytics_event_id`

Add explicit side-effect fields:

- `files_status text`
- `admin_email_status text`
- `admin_email_message_id text`
- `admin_email_sent_at timestamptz`
- `customer_email_status text`
- `customer_email_message_id text`
- `customer_email_sent_at timestamptz`
- `analytics_status text`
- `analytics_sent_at timestamptz`

Use check constraints:

- `files_status`: `not_required`, `pending`, `saved`, `partial`, `failed`
- email statuses: `pending`, `sent`, `failed`, `skipped_unconfigured`
- analytics status: `pending`, `sent`, `failed`, `skipped_unconfigured`

The migration leaves status fields null on historical rows, where null explicitly means “legacy outcome unknown.” The new API writes an initial status for every new row. This avoids falsely labeling every old inquiry as pending. No migration updates old customer data, deletes rows, or changes existing RLS policies. The only new indexes are the two unique partial correlation indexes; status indexes are omitted because there is no worker querying them yet.

Update `supabase/schema.sql` to represent the desired fresh-install schema, but do not treat that file as an executed migration.

## 7. Environment Variable Design

Use server-only variables:

- `GA4_MEASUREMENT_ID`: the GA4 web-stream measurement ID used by Measurement Protocol.
- `GA4_API_SECRET`: a Measurement Protocol API secret created manually in GA4 Admin.
- `RESEND_API_KEY`: existing Resend credential.
- `INQUIRY_NOTIFICATION_EMAIL`: existing comma-separated administrator recipients.
- `INQUIRY_FROM_EMAIL`: existing verified sender.
- `NEXT_PUBLIC_SITE_URL`: existing canonical site origin used for safe absolute links.

Continue supporting the existing browser variable `NEXT_PUBLIC_GA_MEASUREMENT_ID` or `NEXT_PUBLIC_GA_ID` for client page and micro events. Never expose `GA4_API_SECRET` through a `NEXT_PUBLIC_` name.

If the two server GA variables are missing, the lead remains saved and `analytics_status` becomes `skipped_unconfigured`.

No environment file is read or edited during implementation. Required values are documented only.

## 9. Request and Processing Flow

### 9.1 Client

1. On the first unsent form journey, generate one UUID idempotency key and store it in `sessionStorage`; reuse it across retries and same-tab reloads until a saved-inquiry response is received.
2. Capture the landing pathname and allowlisted UTM values once per session.
3. Resolve GA client/session identifiers on a best-effort bounded timeout; failure does not delay submission indefinitely.
4. Send the idempotency and sanitized acquisition fields in `FormData`.
5. Emit `quote_cta_click` before the request.
6. Treat `success: true` as “inquiry saved,” then render any returned warnings for failed files, email, or analytics without exposing internal secrets.
7. Do not emit any client success event.

### 9.2 Server

1. Parse `FormData`.
2. Validate required text fields and the idempotency UUID.
3. Validate acquisition fields with a separate allowlist schema.
4. Validate file count, size, extension, and non-empty file objects before any database insert.
5. Attempt to insert the inquiry with `idempotency_key`, acquisition fields, `analytics_event_id`, and initial statuses.
6. On a unique idempotency conflict, read the existing row by key and return its ID/statuses without creating a second row or resending completed side effects.
7. Upload each validated file and insert each `inquiry_files` row. Check both errors. Persist `saved`, `partial`, or `failed`.
8. Send the administrator notification and explicitly inspect Resend's returned `error`. Persist message ID/status.
9. Send the customer confirmation independently and persist message ID/status.
10. Send one Measurement Protocol `generate_lead` and persist `sent`, `failed`, or a skipped status.
11. Return business success because the inquiry exists, together with side-effect statuses and human-readable warnings.

Every server stage emits a structured, privacy-safe log containing the internal inquiry ID, stage, outcome, and a bounded error code. Logs must not contain names, email addresses, telephone numbers, message text, raw attribution query strings, or file names.

If the initial inquiry insert fails for a reason other than an idempotency conflict, return a 500 and do not attempt files, email, or analytics.

## 10. Partial Failure Semantics

- Database failure: request fails; there is no lead.
- Invalid or excessive file before insertion: request returns 400; there is no lead and no orphan row.
- Storage or file-record failure after insertion: lead remains saved; files status is `partial` or `failed`; administrator/customer messages and analytics may still proceed; response includes a file warning.
- Administrator email failure: lead remains saved; customer email and analytics proceed; status is `failed`.
- Customer email failure: lead remains saved; administrator email and analytics remain independent; status is `failed`.
- Analytics failure: lead remains saved and emails remain unaffected; status is `failed`.
- Missing external configuration: relevant status is `skipped_unconfigured`, not `sent`.
- Duplicate idempotent request: returns the original inquiry with `duplicate: true`; it does not create or count a new lead.

The success UI must not claim that a confirmation email “is on its way” when `customer_email_status` is failed or skipped.

## 12. Testing Strategy

Add Vitest because the repository has TypeScript modules and needs deterministic dependency mocking. Production modules must expose focused dependency boundaries rather than embedding test-only branches.

Tests must be written before production behavior and observed failing for the expected reason. Required cases:

1. valid inquiry: one insert, correct statuses, one server analytics event;
2. invalid file extension: 400-equivalent result before any insert;
3. oversized file: rejection before any insert;
4. too many files: rejection before any insert;
5. database failure: no storage, email, or analytics calls;
6. storage failure: inquiry remains saved, files status failed/partial, explicit warning;
7. `inquiry_files` insert failure: explicit partial status, not silent success;
8. Resend returns `{data:null,error}`: email status failed even without an exception;
9. duplicate idempotency: one row, one analytics attempt, duplicate response returns existing ID;
10. analytics non-2xx or network failure: inquiry and email results remain intact, analytics status failed;
11. missing GA environment: inquiry succeeds, analytics status skipped;
12. acquisition sanitizer strips query/hash/credentials and rejects PII-shaped unknown inputs;
13. response messaging does not promise a customer email when email delivery failed.
14. structured logs and analytics payloads contain no customer PII or file names.

Validation commands after implementation:

- `npm run typecheck`
- `npm run lint`
- `npm run test`
- `npm run test:seo`
- `npm run build`
- `git diff --check`

The final report must include test names/counts, pass/fail totals, command exit codes, and any warnings. It must not summarize this only as “passed.”

## 14. Acceptance Criteria

- Local code produces exactly one canonical server-side lead attempt per unique inquiry.
- A repeated request with the same idempotency key cannot insert another inquiry.
- Every side effect has an explicit persisted state.
- No invalid attachment can leave a newly inserted inquiry.
- No Resend API error is treated as sent.
- Analytics failure cannot remove or invalidate the inquiry.
- No PII is included in the GA4 payload.
- English and German contact paths are visible through normal GA page views.
- All required automated commands complete and are reported concretely.
- No production database, GA4 Admin, deployment, commit, push, or live inquiry is performed.
